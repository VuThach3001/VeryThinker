# Reviewed parameterized recipes

Recipes make common assignments repeatable: Sol reviews requirements, interfaces, coverage classes, expected values, oracle rationale, and tolerances before a worker generates implementation and runs checks. Version 1.0.0 includes Cornell evidence notes, scalar configuration persistence, and embedded hysteresis load control.

`resolveRecipe(id, version)` returns the catalog identity, applicability, limitations, parameter shape, and a hash covering its catalog and executable generator. `prepareRecipe(root, input)` validates parameters, creates or uses a bounded task, and writes an instance with its design, check, requirement fingerprints, and protected artifacts. `runRecipe(root, id)` requires current separate reviews of the design and verification plan, validates the frozen inputs, preserves authored output changes, generates implementation, and collects actual check evidence through the shared core.

Protected parameters, expected results, and verification code live under `.verythinker/recipes/<instance-id>/`. The instance records hashes of those files and the design/check records. `verifyFrozenRecipe(root, taskOrInstance)` detects changed parameters, requirements, recipe implementation, or protected artifacts. It supports dispatch and completion gates. Archives must include these artifacts and the exact recipe version/hash.

Prepared design and check records are drafts. The native Sol architect and verification strategist stamp their actual invocation provenance and review the complete contracts before workers start. Execution provenance fields alone can be added to those drafts without changing the frozen engineering contract. Changes to substantive parameters or expectations require a reviewed recipe revision. In strict execution, a developer generates artifacts and returns `verification_pending`; a separately bound check executor performs the prescribed procedure and collects evidence.

After inspecting a generated design, its architect uses the bound `record_update` operation with that design ID and `data: {}`. A verifier adopts the generated check through the same operation under its own native invocation. The gateway supplies their actual provenance; their respective `architect` and `verifier` ownership and existing task/workflow bindings remain unchanged. This preserves the protected contract fingerprint without resealing it. Each author completes its assignment report and inference turn before a separate reviewer approves the sources. Body, links, owner, or other contract changes require a reviewed replacement.

Software verification derives shape, type, inclusive-bound, enum, missing-file, round-trip, malformed-file, and invalid-save preservation cases from the declared contract. Expected records remain independent of the implementation: validation and persistence receive disposable copies, so mutating an input cannot change its expected result. Every declared invalid save case must preserve stored bytes; failed malformed-file loads must preserve the malformed input. The generator supports integer, finite number, string, and Boolean fields. It does not provide nested objects, migration, concurrent-writer serialization, or power-loss durability.

Embedded verification partitions the entire bounded ADC domain for both prior states and adds fault, overflow, invalid-state, hysteresis-history, and ideal-circuit expectations. Generated C is optionally compiled and executed with a host compiler. Optional command-line ngspice measures two ideal DC points against the reviewed Ohm-law expectations and relative tolerance. Without those tools, the evidence explicitly reports that native C or SPICE was not requested. Simulation does not establish physical hardware safety, timing, or board performance.

Cornell verification checks format and artifact separation. Note provenance/freshness validation and independent semantic review remain required.

`reviseRecipe(root, id, { change_id, parameters, reason })` requires a linked reviewed change and produces a replacement instance with fresh design/check artifacts. The old instance remains historical. Workers escalate a genuine oracle or specification problem; a reviewed correction precedes fresh execution. Successful unsupported procedures can become reviewed recipe candidates later.

Preparation identity includes the generator hash and requirement fingerprints. A reviewed generator/oracle or requirement correction can preserve the same parameters while producing a distinct replacement; retrying that reviewed revision reuses its replacement identity. Ordinary preparation refuses to silently reuse an instance whose generator or requirements changed. Protected expectations still require fresh reviews before execution.

The generator hash identifies the implementation loaded by that process. If rebuilding or upgrading changes its module on disk, new preparation stops until the native transport is restarted or resumed into a fresh process. Existing instances retain their captured generator identity; a changed generator requires the reviewed replacement workflow. Preserve genuine invocation and project history when resuming.

A reviewed replacement may reuse its output paths when existing content still matches the prior generated-file hashes. Authored changes are preserved and require a new output path or an explicit integration decision. The old design/check remain superseded history; the replacement collects fresh verification. Cornell narrative revisions use new visible artifact paths to preserve the original note and its provenance.

A reviewed revision retires explicitly referenced predecessor instances only when they share its task, workflow, and recipe identity. Their records, protected files, and implementation history remain intact; other recipes or tasks mentioned as context remain active. The replacement records its retired IDs and supersession links, and retries reuse that identity. Reused output bytes must match a generated hash from that reviewed predecessor set; authored changes remain protected.
