# Native model routing and invocation evidence

VeryThinker alpha.3 uses a project-local Codex App Server to request a specific model, capture its native acknowledgment, and observe the actual inference turn. Strategic roles request `gpt-6.1-sol` with high reasoning effort. Routine roles request `gpt-6-luna` with medium reasoning effort; `gpt-5.6-terra` is allowed only after a native unsupported or unavailable model error for Luna.

The bridge uses the user's existing native Codex authentication, provider, and global approval settings. Strategic roles restrict native shell access to read-only and require the native acknowledgment of that restriction; workers inherit the existing sandbox policy. Each thread exposes only its role's VeryThinker MCP operations. The approved workflow authorizes these bounded operations automatically, so the bridge configures their supported per-tool `approval_mode: approve` and records the scoped gateway configuration hash. Authored tool approval or discovery restrictions are preserved as conflicts requiring review. The bridge never replies by approving a pending native request. A native approval request remains `waiting-native-permission` until the owning host acts or the invocation is interrupted. Authentication, network, rate, and quota failures are blockers rather than reasons to select another model.

## What establishes a routed invocation

`thread/start` or `thread/resume` must acknowledge the exact requested model, provider, reasoning effort, project directory, and native thread identity before generation starts. `turn/start` supplies a turn identity. A successful `turn/completed` event establishes completed inference for that request. A model catalog entry does not establish account access. These semantics follow the [official Codex App Server integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) and [App Server protocol documentation](https://learn.chatgpt.com/docs/app-server).

The acknowledgment describes native model selection. It is not separate backend attestation. VeryThinker detects the native `model/rerouted` event and blocks the affected output; missing model provenance is also a blocker. Strategic acceptance requires a successfully completed invocation and current configuration. While a worker is running, invocation-bound MCP operations may write the records that the completed turn will later substantiate.

## Runtime and receipt storage

The isolated runtime is `@openai/codex@0.162.1`, installed with npm integrity verification and lifecycle scripts disabled under `.verythinker/tools/codex`. The package version, integrity, installed native binary hashes, and generated protocol hashes are recorded in `.verythinker/native-runtime.lock.json`. A changed executable or protocol requires review before execution. Platform binary packages retain their Apache 2.0 license independently of VeryThinker's MIT source.

Receipts are authoritative JSON artifacts at `.verythinker/native/receipts/<invocation-id>.json`. They bind the project, role, workflow/task, request identity, execution mode, selected model, native thread/turn, runtime, relevant configuration, completion, fallback evidence, reroutes, permissions, and bounded returned output. The bridge signs each lifecycle update with Ed25519. Free-form model strings supplied by a worker cannot create a receipt. Dependency-injected transports are always signed as `protocol-fixture`; strict routing rejects them even if their simulated turn completes or their model strings match.

Public verification keys are stored under `.verythinker/native/keys`, with the project trust registry in `.verythinker/native/trust.json`. The private signing key remains in `.verythinker/cache/native/private-key.pem`; archives exclude it. Restored archives can verify historical signatures using preserved public keys and trust data. A new local execution generates a new signing key if the private cache is absent. This is a local integrity boundary, not protection against a user or process with unrestricted access to the entire project and its private cache.

## Ownership, interruptions, and resumption

One process owns each running invocation and its App Server transport. A request ID is idempotent only for the same prompt, role, workflow, and task. Project-level dispatch serialization enforces at most the configured three routine/strategic workers in addition to the coordinator. Another invocation cannot start the same active task.

Interruption stops the owned native turn and preserves its receipt. Resume creates a fresh invocation receipt, preserves the prior identity, acknowledges selection again, and reconciles any previous native turn before starting a new one. A missing owner or a still-live orphaned transport is a blocker requiring reconciliation; the bridge does not duplicate work blindly. Wait operations are bounded to 60 seconds, and timed waits retain running state. MCP transport closure stops only the native children owned by that server and closes its capability sessions.

Installed role and workflow instructions are preloaded into the native thread. `project_read` supplies bounded, hashed text from assigned source and evidence paths without needing a shell command merely to inspect those inputs. Private signing keys, credentials, raw sessions, native tool caches, and Git internals are excluded. This supports a Windows installation whose native read-only shell helper is unavailable while retaining its native permission boundary. Prescribed implementation and verification still use approved core/recipe operations and actual evidence.

Generated recipe contracts remain drafts until their actual role adopts them. The architect inspects the generated design and the verification strategist inspects the generated check; each uses `record_update` with empty data to bind that unchanged definition to their own native invocation. This provenance-only adoption does not change the protected contract or its oracle. Authors complete their assignment reports and inference turns before a separate reviewer assesses the resulting definitions. Review findings contain unresolved defects only: a passing review has an empty findings array, while positive observations and rationale belong in its seven-section assignment report.

Captured verification input manifests and content-addressed blobs are readable only through validated references within the assigned workflow or task. A reviewer can inspect the source bytes used by an earlier failing check without receiving access to other increments' private input stores.

The authenticated Windows demonstration encountered a host-specific legacy elevated sandbox refresh failure: runtime ACL validation could not open an existing `cua_node/node_repl.exe` executable because of Windows file-sharing error 32. The pinned command runner and setup helper were installed, and model inference worked. No pending native request was approved, no user process was stopped, and no global sandbox setting was changed. Existing scoped MCP operations provide a permitted recovery path, but this does not prove generic native shell or file-edit compatibility on this host. The [sanitized runtime diagnosis](validation/native-alpha3-windows-runtime.json) separates observed failures, pinned-source findings, and unresolved limits.

The Developer also receives [scoped implementation edits](workspace.md) through `task_file_write`. Its current native receipt must confirm that operation. The Core checks assigned paths, current reviewed plans, protected artifacts, and a fresh expected file hash, preserving previous bytes and completion history. This provides a bounded editing operation without granting a pending native permission request.

## Compatibility and verification limits

Projects initialized through the older core API retain legacy behavior when `.verythinker/routing.json` is absent. Alpha.3 installation and migration add the approved routing policy. Authored model-policy changes are preserved as a migration conflict rather than silently rewritten. Historical accepted records remain historical evidence; new managed work requires native routing receipts.

The `0.153.4` and `0.162.1` fixtures retain observed protocol shapes. Fake App Server tests establish acknowledgment parsing, receipt integrity, routing gates, fallback restrictions, interruption, timeout, and permissions behavior. The fake process does not authenticate or perform inference. A production routing claim additionally requires an authenticated native demonstration using the pinned runtime and the requested account models.
