# Scoped implementation edits

Every assigned role uses `task_file_write` to create or replace ordinary UTF-8 implementation and documentation files. It first reads the target through `project_read`, then supplies that exact SHA-256 as `expected_hash`. A new file uses `null`. The operation requires an observed running invocation for the task's current owner, approved task paths, and current reviewed design and verification plans. Historical receipts that did not expose this capability cannot authorize it.

The core API is `workspaceWrite`. The administrative CLI, `workspace write --data JSON`, calls the same guarded function and requires a genuine invocation identity; it does not offer an unrestricted editing shortcut. The invocation-bound MCP gateway supplies the receipt identity itself. A reviewer inspecting another producer's work has read-only artifact access; a reviewer-owned documentation producer can edit its assigned files and requires a different taskless reviewer thread for final review.

Edits are limited to 128 KiB of valid UTF-8 per file. Binary files, deletions, linked files, Windows path aliases, managed storage, native instructions, tool installations, and credential paths are rejected. Protected verification scripts, recipe expectations, and oracle artifacts retain their separate reviewed change process. Cornell notes, exercises, answers, and user-written solutions use their existing ownership and revision operations.

Each edit preserves the exact previous file and task bytes, proposed bytes, original invocation, intent, and completion receipt beneath `.verythinker/evidence/workspace-history/<task>/<operation>/`. Task output references include these artifacts so archives can retain the history. Completion is recorded only after replacement and verification of the resulting file hash. Incomplete or changed history blocks engineering gates. A later legitimate edit does not erase earlier history; current verification evidence still has to match the current implementation.

Use the same operation UUID and unchanged payload when recovering a lost response. Unknown current bytes are preserved and reported as a conflict. Cooperative Core edits serialize and check fresh bytes immediately before replacement. This is an optimistic filesystem check; Node.js does not provide a kernel compare-and-swap against an unrelated editor, and the file plus its task record are not one filesystem transaction. Durable history makes those interruption boundaries visible instead of describing an incomplete edit as successful.

After a genuine native interruption, resume the original producer invocation and its task. The fresh receipt must establish signed resume lineage for the same role, workflow, and task. Recovery preserves the original intent author and records the replacement invocation separately. Only an intact pending operation with its original payload and known old or proposed bytes can pass the temporary recovery readiness check; normal verification remains blocked until completion is recorded.

This capability supplies a bounded implementation path when the native Windows edit helper cannot operate. It does not change the native sandbox, approve a pending permission request, or establish unrestricted shell compatibility. See [native runtime observations](native-runtime.md) and [validation](validation.md).
